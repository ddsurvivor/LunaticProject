# 修复汇报与验收证据管理

更新：2026-11-07。适用于每次修复结束后产出的汇报文档。修复无需长报告时，可只更新原任务记录；一旦产出报告，就必须登记、附实际截图并列明清理范围。

## 可直接追加的提示词

```text
每次修复完成后，如果产出了汇报文档，请同时完成以下收尾：

1. 在 Docs/修复汇报索引.md 登记任务编号、日期、修复结论、报告链接、截图、证据目录和验收状态。开发验证通过与用户验收通过分开记录，未经用户确认不要标为已验收。
2. 将新增详细汇报、截图、日志、测试输出和临时脚本集中放在 tmp/Reports/<任务编号>-<日期>/，由 Git 忽略。正式开发文档保留简短实现说明、结论和索引，不混入生成结果。
3. 在报告正文就近嵌入真实截图，不只写截图文件名。注明场景、分辨率、复现/验证步骤以及截图证明了什么。界面问题尽量给出修复前后对照；非视觉问题可以附实际运行、控制台或测试结果界面的截图，同时链接原始日志。没有真实截图时写明“未截图”和原因，不把示意图或历史图片当成本次运行证据。
4. 报告分清本次通过、未执行、既有问题与剩余边界，附复现步骤。已有截图可以引用，无需为补文档重复执行已通过且未变化的测试。
5. 报告末尾提供清理清单：可删除的任务专属目录、散落的临时入口、必须保留的正式文件。优先让本次汇报与证据能按一个任务目录整体清理，不把共享隔离工程根目录列为删除目标。
6. 验收前保留材料。只有用户要求清理或已有明确清理约定时才删除；先核对绝对路径及任务归属。清理后将索引标为“已验收／证据已清理”，记录日期并保留简短结论，移除正文中失效的截图引用和证据链接，不删除正式实现或其他任务资料。
7. 最后回复提供报告及索引链接，说明截图是否齐全、验收状态和可清理范围。
```

## 存放与报告要求

建议结构：

```text
tmp/Reports/B43-20261107/
  report.md
  screenshots/
  logs/
  results/
  tests/
```

报告至少包含：任务与日期、问题和触发条件、修复内容、实际验证结果、截图及说明、未覆盖范围、清理清单。本地截图使用当前查看环境可预览的绝对路径嵌入，同时在清单记录仓库相对路径，方便迁移与清理；最终答复中的本地文件链接也使用绝对路径。

截图是辅助证据。运行界面不能单独证明错误数为零或存档未变，应同时链接测试输出、日志或哈希对照；纯规则或数据修复不得仅凭画面宣布验证通过。涉及存档、隐私或令牌的画面，选择不暴露敏感内容的实际界面进行截图。

任务编号沿用开发计划；没有编号时使用明确任务名和日期，不为了产出汇报擅自分配开发任务。

## 登记、验收与清理

- 入口为[修复汇报索引](修复汇报索引.md)。状态建议使用“待用户验收”“待补充证据”“已验收／证据保留”“已验收／证据已清理”。自动测试通过不等于用户已经验收。
- 本规则从现在起适用于新增报告。此前已在Docs中的正式记录可继续保留，不为统一目录批量搬迁或删除；登记其报告与现有证据位置，补上可用的真实截图。
- 验收后只清理清单列出的任务专属文件。位于共享隔离工程中的任务子目录可单独列出，但不能删除整个共享工程、正式脚本、实际存档或其他任务目录。
- 清理时保留Docs中的简短结论与索引。临时报告删除后将原链接改为“报告已清理”，保留结论和日期；正式记录若保留，应同时移除已清理截图的失效图片引用。
- 验收前用户也可明确要求清理，按其指令执行并如实保留“未验收／证据已清理”的状态；不能据此补记验收通过。
