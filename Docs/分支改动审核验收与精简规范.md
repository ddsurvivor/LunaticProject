# 分支改动审核、验收与精简规范

适用于当前开发分支相对 `dev` 的代码审核与精简。遵循 [AGENTS.md](../AGENTS.md)、[代码注释规范](代码注释规范.md)及[修复汇报与验收证据管理](修复汇报与验收证据管理.md)。更新：2026-11-08。

## 可直接使用的提示词

```text
请审核并精简当前分支相对 dev 的实际改动，并完成针对性验收。

1. 先读取项目规范与相关任务记录，确认已接受的设计、已跳过的任务和验收范围；不把 TODO 或推测当作新增需求。
2. 记录当前分支、HEAD、dev、merge-base 与工作区状态。分别检查 dev...HEAD 的提交差异和工作区实际差异，覆盖暂存、未暂存及未跟踪源码和必要资源。明确采用本地还是远程基线，不擅自更新分支。
3. 修改前保存本轮涉及文件的清单、哈希和必要快照。保留已有修改；不擅自提交、合并、重置、暂存、删除旧证据或清理其他任务文件。
4. 先审核行为正确性，再判断可精简内容。重点检查结算和扣费、状态与回合计时、异步/聚能回调、对象复用、暂停与转场、存档回滚及 UI 资源绑定。问题给出等级、位置、触发条件、影响和可验证依据；尚未证实的疑点单列。
5. 在授权范围内修复确认的问题，并精简重复逻辑、无效分支、已证实无用的实现或不必要的临时分配。优先小范围共用实现；不为减少行数改变玩法、取消保护、过度抽象或改写无关代码。没有发现问题时如实说明，不凑数量。
6. 删除或改名之前检查代码调用、反射、UnityEvent、Unity/Odin 序列化、场景与 prefab 继承；文本搜索不到引用不能证明安全删除。保留兼容字段和手调布局，避免批量重序列化。新增或修改行为时同步维护注释。
7. 对实际修改做匹配风险的验证：编译只是第一步。精简尽量对照前后同一输入的结果；修复需要证明原问题和修复结果。涉及 UI 要运行实际场景并截图，涉及奖励和存档要验证提交/拒绝/回滚及文件未被意外改写。随机路径记录种子；时间路径确认实际推进，不能用冻结画面冒充测试。
8. 临时测试、替身、输出和报告放 tmp/Reports/<任务编号>-<日期>/；正式代码不依赖测试类型。优先使用隔离工程或临时档案，执行后撤销临时入口，并确认主工程和真实存档没有被污染。
9. 保存首轮失败和修正记录。区分产品问题、测试自身问题与既有问题；不要覆盖失败日志后只保留绿灯。不能执行的项目写明原因和影响，历史通过不能代替本次运行。
10. 完成后对照修改前清单复查实际变更范围，记录修复/精简文件、行为差异、验证结果与剩余风险。统计行数和文件数只作辅助，不能作为验收标准；没有可信性能测量就不宣称速度或内存提升比例。
11. 如产出汇报，正文嵌入真实截图并说明场景、步骤、分辨率和证明范围，链接原始检查结果；登记 Docs/修复汇报索引.md。列明本任务可清理目录与必须保留文件，验收前保留材料。
12. 最终答复先说明确认的问题及处理结果，再给出精简内容、测试结论、未覆盖范围和规范/报告链接。开发验证通过标为“待用户验收”；不自行标为已验收或合并就绪。
```

## 基线与范围

| 对象 | 用途 | 注意事项 |
| --- | --- | --- |
| `git diff dev...HEAD` | 审核从共同祖先引入的已提交修改 | `dev` 与当前分支同提交时可能为空，不能据此宣布无改动 |
| `git diff dev` | 本地 `dev` 相对当前工作树的受跟踪文件差异 | 同时覆盖暂存和未暂存的最终内容；若分支分叉，须与提交差异分别解释 |
| `git status --short`、`git ls-files --others --exclude-standard` | 补齐未跟踪实现与资源 | 新增源码、`.meta`、配置和 prefab 也属于审核对象；忽略目录不强制加入 Git |
| 本轮修改前快照 | 区分已有开发与本轮审核产生的修改 | 保存路径、哈希、分支提交和任务范围；有并行改动时先核对归属再处理 |

按需核对暂存区差异，避免把已经暂存但工作树再次修改的内容漏掉。基线默认是本地 `dev`；需要远端最新状态时明确记录来源和提交。审查源码时追踪其依赖的资产与入口，但不自动扩大为全部历史任务重新验收。

## 问题与精简记录

每项确认问题记录：优先级、文件/接口、复现输入、实际与预期结果、影响范围、处理和回归证据。P0 为阻断或严重数据损坏，P1 为高影响错误，P2 为一般功能问题，P3 为低影响问题。纯可维护性建议不包装成运行错误。

精简先说明“不再重复做什么”以及保持的行为契约，再说明实现方式。抽取公共函数需核对各调用点的细微差异，例如：普通新建 Text 与嵌套 prefab 的覆盖记录、实时与暂停时间、预览与真实结算、当前生命与旧生命回调。不能用一个过宽的公共接口抹掉这些区别。

Unity 专项要求：

- 检查场景和 prefab 中的组件 GUID、fileID、序列化字段及持久化事件；对 Odin 数据不能只检查可读 YAML 表面内容。
- 需要 Editor API 修改资产时优先使用正式加载/保存接口，比较实际变化对象块，排除无关序列化改写。
- 判断生命周期时查看统一属性或基础类实现，不因为子类没有单独设置变量就断言缺陷。
- 共用缓冲区必须每轮刷新，验证隐藏/重新显示、移除/重新登记、销毁与重载边界，避免以减少分配换取残留数据。
- 改 UI 定位时至少核对相关分辨率、屏幕边缘、遮挡避让及状态展开；截图与几何/交互检查共同作为证据。

## 验收与交付

| 阶段 | 必须留下的结论 |
| --- | --- |
| 审核 | 实际覆盖文件和路径、确认问题、尚未证实疑点、保留的兼容设计 |
| 修复/精简 | 本轮修改清单、保持或修正的行为、未采纳精简及理由 |
| 验证 | 实际命令/入口、环境、前后结果、失败记录、未执行范围 |
| 收尾 | 最终差异复查、临时入口状态、存档及正式资源保护结果 |
| 汇报 | 报告及截图、索引、待用户验收状态、任务专属清理清单 |

详细报告及截图遵循证据管理规范，正式文档仅保留必要结论和入口。无法截图时明确记录“未截图”及原因，不因此虚构运行验证。清理只在用户要求或已有明确约定后进行；保留正式代码、规范、计划、简短结论和索引。
